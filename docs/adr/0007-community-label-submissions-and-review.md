# ADR 0007 — Community label submissions and Confirmed-tier review

Status: Decided 2026-10-21 (implemented in `packages/features/community-labels/`)

## Context

ADR 0004 designed two public label tiers — **Community** (anyone submits, with a required source)
and **Confirmed** (a moderator reviews and confirms) — and said `Label` needs a `reviewStatus`
field separate from `confidence`. ADR 0006 then built accounts and roles, and resolved who can be
a moderator. Before this change there was no way for a person to submit a label at all: only the
ingestion scripts (OFAC, UK Sanctions List, Safe deployments) wrote labels.

Building it forced four decisions ADR 0004 left open.

## Decision

### 1. `reviewStatus` exists only on labels a person submitted. Ingested labels have none.

`Label` in `@osstrace/core` is now a union:

- `IngestedLabel` — `reviewStatus?: never`. The type forbids the field.
- `CommunityLabel` — `reviewStatus: "community"`, plus `submissionId`, `submittedBy`, `submittedAt`.
- `ConfirmedLabel` — `reviewStatus: "confirmed"`, plus the above and `confirmedBy`, `confirmedAt`.

Every variant still requires `source` (ADR 0002). `isSubmittedLabel(label)` tells them apart.

Why ingested labels aren't forced into `community` or `confirmed`:

- **`community` would be false.** It means "a person claimed this and nobody has checked it".
  An OFAC designation wasn't claimed by a contributor. It's the U.S. Treasury's own published
  list, ingested by a script.
- **`confirmed` would also be false.** It means "a moderator of this project reviewed this
  submission". Nobody here reviewed the ~150 ingested labels one by one, and as datasets grow
  nobody should have to. Their authority is the cited publisher. Labelling them "confirmed" would make the badge mean
  two different things and would overstate what this project did.
- **They're corrected a different way.** You fix an ingested label by re-running its script
  against the publisher's current list, not by moderation. They don't belong in a review queue.

**Why there's no third value like `"official"` or an `origin` field.** It would mean rewriting
every ingested dataset and every ingestion script to add a field that carries no information the
type doesn't already carry, and the review queue would still have to exclude those labels. With
the current shape, "has no `reviewStatus`" is typed rather than a convention. `IngestedLabel`
says what it means, and a label can't be both ingested and reviewed.

### 2. Submissions live in their own feature package and their own store, not in `data/labels/`

`@osstrace/community-labels` owns the **submission** record (`community` | `confirmed` |
`rejected`). A submission isn't the same thing as the label the public sees. It can be
**rejected** (with a reason the submitter sees), and a rejected submission is never shown as a
label anywhere. It's only kept so the decision can be audited.

Storage: `JsonFileSubmissionStore` at `data/community/submissions.json` (git-ignored,
`COMMUNITY_LABELS_PATH` overrides it). It follows the same reasoning as `JsonFileAccountStore`,
because it's written by a live server and read by other processes. It re-reads on every call,
serializes writes and writes atomically. It isn't in `data/labels/` because that directory is
repo seed data regenerated by scripts. This file is one running instance's user-generated data,
and it links account ids to claims. Publishing a vetted export of confirmed labels into the open
dataset (ADR 0005) is a separate, later step. It needs its own licensing/attribution decision
about contributor submissions.

### 3. Community labels are read through a read-only `LabelReader`, after every ingested source

`@osstrace/core` gains `LabelReader` (the read half of `LabelStore`), and `CompositeLabelStore`
takes `lowerPriorityReaders`. These are consulted after every writable store and never written
to. The Explorer (and through it the Visualizer) plugs in `CommunityLabelReader` there. Two
consequences:

- **An official source always wins.** If an address is OFAC-sanctioned, a community label can't
  replace that label in lookups.
- **There's no `addLabel` path for community labels.** The only way one comes into existence is
  `LabelSubmissionService.submit`, which requires a session and a source.

The core model still shows **at most one label per address**. When several non-rejected
submissions exist for one address, the reader shows the most recently confirmed one. If none is
confirmed, it shows the most recently submitted one.

The Explorer used to serve the whole report, labels included, from its 30-second cache. Labels
are now re-read on every lookup, even on a cache hit. Only chain data is cached, so a
confirmation or rejection shows up on the very next lookup.

### 4. Moderation rules

- **Submit:** any authenticated user (`authenticate(token)`). Required fields: chain, a
  well-formed address, a name, `confidence` (`verified` means the source states it outright,
  `predicted` means it's inferred), and `source.url` + `source.description`. The URL must be an
  absolute http(s) URL to a real host with no embedded credentials. The server never fetches it,
  since fetching a user-supplied URL from the server is an SSRF hole. Whether the source actually
  supports the claim is what the moderator checks. `source.addedAt` is the submission date.
- **One pending submission per account per address**, so a user can't flood one address's queue.
  Another user can still submit for that address, and the same user can resubmit after a review.
- **Confirm / reject:** `requireRole(token, "moderator")` (admins pass too). Rejecting requires a
  reason.
- **A moderator can't review their own submission.** Confirming takes a second person. Otherwise
  a single moderator could self-confirm anything, and the badge would mean nothing more than
  "a moderator said so".
- **Each submission gets exactly one decision.** The "still pending?" check and the write happen
  together inside the store's write lock, so two moderators acting at once can't both succeed.
- **Who did what is recorded by account id, never email** (ADR 0006). `submittedBy` and
  `confirmedBy` are public on the label. That's accountability for a public claim, and an opaque
  UUID doesn't reveal the email. Only admins can map an id to an email.

### 5. Its own API server (port 5311), mountable elsewhere

Routes are under `/labels/submissions`, with the same response conventions, bearer auth and
explicit CORS allowlist as `/accounts`. `createLabelSubmissionsHandler` returns `false` for other
paths, so a deployment can mount it next to the accounts routes in one process. The tests do
exactly that.

## Deferred (explicitly not built)

- **Rate limiting** on submissions, the same gap as login in ADR 0006. It's needed before any
  public deployment. *(Since built: 10 per account per rolling hour, ADR 0017.)*
- **Editing or withdrawing** a pending submission, and **un-confirming** a confirmed one. Today a
  wrong confirmed label can only be superseded by a newer confirmed submission.
- **Showing every submission for an address** (lookups show one label, per the core model).
- **Tags** from the community. Submissions are labels only, and tags (e.g. `sanctioned`) still
  come only from ingested sources.
- **Publishing confirmed labels into the open dataset** (`data/labels/`, ADR 0005). It needs a
  contributor licensing decision first.
- **Self-attested tier 3** — still deferred by ADR 0004.

## What would change this decision

- More than one server instance → a database-backed `SubmissionStore` (same interface).
- If confirmed community labels are ever exported into `data/labels/`, the exported copies keep
  their `reviewStatus: "confirmed"` and provenance fields. They still came from a person and a
  review, not from an ingestion script.
